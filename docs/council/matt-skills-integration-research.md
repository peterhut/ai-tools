## Interaction and grilling: verified facts

[Grilling](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/productivity/grilling/SKILL.md) models the interview as a tree of dependent decisions. A round contains every currently answerable question, numbered and accompanied by a recommendation. Questions dependent on unanswered questions wait for a later round. The agent waits for answers, recomputes the frontier, and continues. A pending factual investigation blocks only its downstream questions; facts are researched by the agent, while decisions belong to the user. The skill calls for shared-understanding confirmation before acting on the resulting plan. Local grilling retains all of these rules.

[Grill-with-docs](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/grill-with-docs/SKILL.md) is a minimal user-invoked wrapper that calls `grilling` and `domain-modeling`. [Grill-me](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/productivity/grill-me/SKILL.md) calls only `grilling`. Neither wrapper defines a council or reviewer debate protocol.

Upstream explicitly rejects a fixed maximum question count: completion follows decision coverage, and the user can steer the session to stop or wrap up. This is a statement about **user interviewing**, not a prohibition on bounding an internal review/debate phase. Separately, upstream assigns prevention of uncontrolled recursive agent spawning to the harness; that does not override this task's explicit prohibition on spawning agents. Sources: [question-limits](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/.out-of-scope/question-limits.md), [subagent-recursion](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/.out-of-scope/subagent-recursion.md).

**Integration recommendation:** let grilling govern the user-facing decision tree. Council reviewers should supply concrete evidence, counterarguments, and unresolved choices to that tree. Multiple reports followed by a coordinator summary would not, by themselves, satisfy the user's request for actual subagent discussion. A distinct exchange in which reviewers answer one another's material objections is needed; its design is still open. Do not turn researcher uncertainty about inspectable facts into questions for the user.

## ADR and domain documentation: verified facts

[Domain-modeling](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/domain-modeling/SKILL.md) requires **all three** conditions before offering an ADR: meaningful reversal cost, a choice that would surprise a future reader lacking its context, and a genuine choice among alternatives made for particular reasons. Missing any condition means skipping the ADR. Therefore an unexplained choice prompts investigation; it does not automatically establish ADR eligibility or authorize inventing the original rationale.

[ADR-FORMAT.md](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/domain-modeling/ADR-FORMAT.md) specifies a short title and **one to three sentences** covering context, decision, and reason. Status frontmatter, options, and consequences are optional when useful. It supports proposed, accepted, deprecated, and superseded status. ADRs use sequential filenames such as `0001-slug.md`, with directories created when needed. Domain-modeling also recognizes context-specific ADR locations via a root glossary map; a new council ADR directory is not prescribed.

The skill challenges inconsistent terminology, probes concrete edge cases, checks statements against code, and updates the glossary as terms become resolved. [GLOSSARY-FORMAT.md](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/domain-modeling/GLOSSARY-FORMAT.md) limits entries to concise, context-specific concepts. Domain-modeling excludes implementation decisions and specification material from glossaries. Reading a glossary for vocabulary is explicitly distinct from invoking the discipline that changes it.

**Integration recommendation:** reference this ADR threshold and concise format instead of creating a council-specific competing standard. Separate observed behavior, documented rationale, inferred rationale, and a newly proposed decision. The user has already required unconfirmed rationale to remain proposed; optional proposed-status frontmatter fits Matt's format without making extra sections compulsory. A concise draft can identify an unknown reason rather than asserting agreement or claiming historical intent.

**Integration recommendation:** distinguish proposing documentation from accepting or publishing it. Council's recommendations-and-drafts remit does not inherit domain-modeling's automatic inline glossary edits merely by citing its policy. The current design interview can continue using domain-modeling under its own authorization. Council should read the [context map](../../GLOSSARY-MAP.md), relevant glossary, and relevant ADRs as context; new terminology or revised decisions can be suggested to their owning context.

## Design vocabulary and Design It Twice: verified facts

[Codebase-design](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/SKILL.md) supplies reusable architecture terms: **module**, **interface**, **implementation**, **depth**, **seam**, **adapter**, **leverage**, and **locality**. A module is scale-independent. Its interface includes caller obligations such as invariants, ordering, errors, configuration, and performance, beyond type signatures. Depth concerns capability relative to the interface callers learn, rather than a ratio of lines of code. A seam is where behavior can vary; an adapter fills that role. Leverage describes benefit to callers and locality describes concentration of maintenance knowledge and change.

Its principles include examining what complexity would reappear at callers if a module disappeared, testing through the interface, and justifying variation before introducing a seam. [DEEPENING.md](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/DEEPENING.md) classifies dependencies as in-process, locally substitutable, remote but owned, or truly external, with corresponding testing/adaptation strategies. It gives refactoring and test-replacement instructions when actually performing deepening; those instructions are not council implementation authorization.

[DESIGN-IT-TWICE.md](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/DESIGN-IT-TWICE.md) first frames a chosen interface-design problem, then runs **three or more** parallel agents with deliberately different constraints. Each produces an interface, usage, hidden implementation responsibilities, dependency strategy, and trade-offs. The coordinator presents alternatives, compares depth/locality/seam placement, and recommends a design or hybrid. It does **not** require agents to respond to one another, specify different model families, or define a user interview protocol.

**Integration recommendation:** reuse the vocabulary where architecture is relevant and use existing domain terminology for the objects being discussed. Design It Twice is an optional method for an identified interface question; its alternative-generation workflow is not evidence that council's reviewer-debate requirement is already met. Requiring it on every PR would also replace proportional consideration review with an unconditional redesign exercise.

## Review boundaries and architecture overlap: verified facts

[Code-review](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/code-review/SKILL.md) reviews a diff against a validated fixed point. Its two independent axes are compliance with documented standards and fidelity to the originating specification. It includes a Fowler smell baseline, subordinate to repository standards and explicitly heuristic. A missing spec is disclosed and that axis is skipped. It aggregates the two reports separately without merging or reranking them. There is no agent-to-agent exchange step, family-diversity rule, or requirement to challenge the desirability of the spec.

[Improve-codebase-architecture](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/improve-codebase-architecture/SKILL.md) surveys for deepening opportunities, prioritizing user scope or recently active areas. It reads domain language and ADRs, explores friction, presents an HTML candidate report, then grills through a candidate the user chooses. It references the reusable design and domain disciplines. An existing ADR can be reopened when actual friction justifies it; theoretical alternatives alone are insufficient. A substantial rejection reason may warrant offering an ADR, subject to domain-modeling's eligibility policy. This is a broader candidate-discovery workflow, not specifically review of an implemented change.

The repository's [assess-maintainability](../../plugins/architecture/skills/assess-maintainability/SKILL.md) was inspected at repository HEAD `7251b1d0d233ffe331970fbe0df0da6831d943d8`; it had no working-tree modification at inspection. Its pinned [repository source](https://github.com/peterhut/ai-tools/blob/7251b1d0d233ffe331970fbe0df0da6831d943d8/plugins/architecture/skills/assess-maintainability/SKILL.md) establishes a reproducible revision. It accepts PR, Git, subsystem, or maintenance-question scope. It investigates information hiding and change propagation using selected code/history evidence, tries to dismiss concerns, and recommends maintenance priorities. It distinguishes activity from severity, inference from explicit rules, and present concerns from demonstrated worsening. It permits a quiet assessment with no recommendations and explicitly avoids a merge verdict or refactoring implementation. The [architecture glossary](../architecture-review/GLOSSARY.md) defines its separate assessment context.

**Integration recommendation:** council can consume existing correctness, standards/spec, and maintainability evidence without requiring those complete workflows to run. It should add contextual consideration review and explicit discussion of contested assumptions. Its challenge to requirements must remain labeled advice: it does not make an implementation compliant with a spec it currently violates. Maintainability can be a relevant perspective without requiring a historical survey on every change. Avoid claiming novelty solely for “architecture review” or parallel reviewers, which these existing workflows already cover.

## Composition versus mandatory dependencies

The pinned [README](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/README.md) distinguishes user-invoked orchestration from model-invoked reusable disciplines: a user-invoked skill may invoke reusable model-invoked skills, but not another user-invoked orchestrator. `grill-with-docs` and `improve-codebase-architecture` are user-invoked; `grilling`, `domain-modeling`, `codebase-design`, and `code-review` are model-invoked. The inspected wrappers corroborate this through `disable-model-invocation: true`.

The README encourages small adaptable compositions. [Upstream scope](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/SCOPE.md) and [new-skills policy](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/.out-of-scope/new-skills.md) decline new skill contributions there and explicitly allow publishing personal compositions elsewhere. These are upstream contribution policies, not a ban on a council plugin in this repository.

**Integration recommendation:** use references to the relevant reusable discipline rather than nesting `grill-with-docs` or `improve-codebase-architecture` inside council. A reference that tells an agent to invoke an installed skill creates a real runtime dependency; a conceptual citation alone does not. Absolute `/home/peter/...` paths in this research are evidence locations, not a portable dependency mechanism. Seamless integration does not, by itself, establish that council must depend on Matt's entire plugin, run code-review first, copy its files, or embed its orchestration.

**Integration recommendation:** if council must also work without those installed disciplines, its essential interaction, evidence, and ADR rules need a portable, explicit source with attribution and a maintenance strategy. A fallback or vendored reference is a packaging choice requiring agreement, not something to smuggle in as “integration.” No plugin behavior changed in this research task, so the repository's plugin release/cachebuster/validation flow is not triggered.

## Decisions still needing the user

These questions are design decisions for the ongoing interview; they are not requests for facts the agent can inspect.

1. **Debate and user interaction:** should reviewers exchange challenges before the first user round, or also return after user answers materially change an assumption? Recommendation: establish independent initial views, require direct responses to material objections, and reopen affected discussion when answers change its premises. The transport, stopping condition, and proportional budget remain to be designed; an empty disagreement set should not force manufactured conflict.
2. **Existing decisions and requirements:** what evidence should justify challenging an accepted requirement or ADR? Recommendation: a concrete changed constraint, previously unaddressed consequence, or evidence contradicting its assumptions; present the challenge and leave acceptance with the user. This retains room for council's broader remit without repeatedly reopening preferences unsupported by new evidence.
3. **Artifact handoff:** does council return ADR drafts inline, or may it save clearly proposed drafts to the owning context's ADR directory? Recommendation: resolve this explicitly before granting file-writing behavior, while preserving the already agreed proposed status for unconfirmed rationale. The all-three ADR threshold and concise format are already established and need no new threshold decision.
4. **Packaging:** must council work when Matt's skills are absent, or is their installation a declared prerequisite? Recommendation: decide portability before selecting references, vendored content, or required dependencies. Upstream invocation categories favor reuse of disciplines, but do not decide this distribution question.
