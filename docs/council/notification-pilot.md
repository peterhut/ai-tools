**The main tradeoff is preserving history versus paying for durability on the UI path.** The README explicitly says startup refresh reconstructs current state, not past transitions, and leaves transition survival undecided ([README.md:5](/tmp/council-forward-3w06cgcl/notification-tool/README.md:5)). SQLite commits enqueue before return and deletes only after sending ([notifications.py:17](/tmp/council-forward-3w06cgcl/notification-tool/notifications.py:17)). This provides a meaningful persistence mechanism; the two passing tests establish orderly reopen/FIFO and retention after a send exception, not power-loss or abrupt-crash guarantees. Inferred intent is stronger durability; author intent is undocumented.

A remote success followed by interruption before local deletion can replay the same ID. Documented remote deduplication supports this approach, assuming stable immutable event IDs; this is not an exactly-once claim. Pending duplicates preserve the first payload, while deleting a row permits later local re-enqueue. If callers reuse IDs for changed payloads, this changes their behavior. No such caller is supplied. If only current-state refresh matters, the baseline deque is a meaningful simpler alternative. If every accepted transition matters, persistence earns a stronger justification. The distinction between process termination and power loss also matters before changing FULL synchronization.

**UI responsiveness remains unverified.** WAL, FULL synchronization, JSON serialization and transaction completion all occur synchronously in enqueue ([notifications.py:9](/tmp/council-forward-3w06cgcl/notification-tool/notifications.py:9)); the README places enqueue on the UI thread and supplies neither a latency baseline nor an acceptance threshold ([README.md:8](/tmp/council-forward-3w06cgcl/notification-tool/README.md:8)). Usually fewer than 40 updates/minute does not establish acceptable individual-call tail latency. A representative supported-disk measurement against a specified UI target could justify retaining this simple design. A worker or batching could reduce UI storage work, but would introduce ownership, acknowledgement and shutdown coordination, and could change when an enqueue is durably accepted. They are alternatives, not prescribed fixes. R2 withdrew its nonrepresentative, untraceable tmpfs timings as support for any conclusion.

**SQLite meets the existing deployment decision.** Standard-library local storage introduces no separate service and fits accepted ADR 0001 ([ADR:6](/tmp/council-forward-3w06cgcl/notification-tool/docs/adr/0001-local-standard-library.md:6)). No changed context supports reopening it. The new directory, connection lifecycle, stored schema and JSON constraints are modest real obligations. Their cost can be proportionate when durability is required; the memory queue avoids them if history is unnecessary. No migrations, broker, quarantine system or other machinery is justified by evidence of a present need.

**An objection changed a conclusion.** R2 initially called a reproduced cross-thread ProgrammingError a concrete defect and suggested a cheap fix. R1/R3 privately examined the added thread-ownership item; R3 and the moderator challenged the defect label because the fixture promises only UI-thread enqueue and contains no sender/caller threading contract. R2 explicitly retracted the defect label and the cheap-fix prescription. SQLite's connection ownership restriction is established; an integration violation is not. Sharing a connection or locking around network sending creates further tradeoffs. If all access uses the creating thread, that restriction is satisfied, although synchronous sending still needs consideration for responsiveness.

R2 also accepted R3's correction that a repeatedly failing oldest event already blocks subsequent delivery in the baseline. Persistence newly carries that obstruction and historical payloads across restarts. Whether to replay all history, coalesce, expire, or quarantine depends on transition/freshness and ordering requirements absent from the fixture. Remote ID deduplication alone does not settle stale distinct transitions.

**Recommendations and necessary questions.** Keep the accepted local standard-library ADR. Do not add operational mechanisms or relax durability merely on speculation. Resolve these product/integration premises, then validate the selected branch:

1. Must successful enqueue preserve every transition across process restart, across machine/power failure, or is startup current-state refresh sufficient? If history is required, retain local persistence as the leading approach; otherwise the deque remains credible. Also specify whether historical replay may delay current state and whether recovery has a deadline.
2. What maximum UI blocking/tail latency is acceptable on supported storage? Measure representative enqueue latency against it before selecting direct commits, batching or a worker.
3. Which thread creates the queue, enqueues and drains/sends? Preserve same-thread ownership if that meets responsiveness needs; otherwise design ownership and durable acknowledgement explicitly.
4. Do IDs identify immutable JSON-compatible events? If yes, first-pending-payload deduplication is plausible; if IDs carry revised payloads, the semantics need a deliberate decision.

These are questions for the readout, not requests awaiting answers during this run. No accepted ADR was reopened, and no new ADR file was written: the central rationale remains conditional on an unchosen requirement.
